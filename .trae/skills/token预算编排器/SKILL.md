# Token 预算编排器

## 何时使用

- 用户给出「一个预算 + 一个目标」，例如："用不超过 N token / $X 完成这件事"、"你自己决定怎么花这个预算"。
- 用户想在有限预算内把任务做完，且允许你自行取舍深度和广度。
- 用户在长任务中担心上下文爆掉或成本失控。

不适用：预算充足、任务单步、或用户明确要求"别省，做到最好"。

## 四条不可动摇的原则

1. **先侦察再分配**：任何分配前，先用低保真侦察拿到任务结构，绝不拍脑袋分区。
2. **边际收益均衡**：预算要往「不确定 / 高价值 / 错了代价大」的地方倾斜；已经确定的部分少花。
3. **硬停止 + 优雅降级**：预设硬上限，触顶就停；但正确性关键步骤不允许因省钱而降级质量。
4. **可测量优先于可解释**：没有 token/cost 计量就无法验证"更高效"，先接线再优化。

## 可分配的是"杠杆"，不是"token 数"

模型无法直接控制自己的 token 数，只能控制以下杠杆。所有分配决策必须落到这些具体旋钮上：

| 杠杆 | 具体手段 | 影响 |
|---|---|---|
| 思考深度 | `thinking.budget_tokens` / `reasoning_effort` / `thinking_budget` | 单步成本与质量 |
| 模型档位 | 贵模型 vs 便宜模型 / 级联 | 单位成本 |
| 子任务数量 | 是否拆分子任务、是否并行 | 总调用次数 |
| 检索/工具次数 | 搜索、读文件、调 API 的次数 | 上下文膨胀 |
| 上下文长度 | 是否压缩、是否只喂相关片段 | 输入 token |
| 缓存 | prompt cache / 语义缓存 | 有效单价 |

## 分配协议（话术模板，可直接抄进 prompt）

```
你是一个预算编排器。用户给定了预算 B 和目标 G。按以下四步执行：

Step 0 · 侦察（不超过 B 的 5%）
  用最便宜的方式（低思考预算 / 小模型 / 单次检索）拿到任务骨架：
  有哪些子问题？各自的不确定性和出错代价？

Step 1 · 分解与估值
  把 G 拆成 2–7 个子任务。给每个标注：
  - 价值 V（对最终结果的贡献）
  - 不确定性 U（当前有多不了解）
  - 风险 R（做错的代价）
  优先级 = V × U × R，而不是平分。

Step 2 · 分配
  按下面的默认策略给出每个子任务的配额，并明确写出用哪个杠杆：
  - 若某子任务 U 高且 V 高 → 高思考预算 + 允许多次检索
  - 若某子任务已基本确定 → 低思考预算 + 单次执行，不重复验证
  - 若子任务彼此独立 → 并行，但先确认并行不增加总成本
  预留 20% 预算作为"事后校验与补救"。

Step 3 · 执行与再分配
  每完成一个子任务，用实际消耗对比配额：
  - 若提前完成 → 把剩余额度转给下一个高 U 子任务
  - 若即将超支 → 先降杠杆（降思考预算/换便宜模型/减少检索），
    而不是砍掉校验步骤

Step 4 · 停止与交付
  满足任一条件即停：
  - 结果已达可交付标准
  - 硬预算到顶
  停止时明确报告：实际消耗 / 预算、哪些子任务被降级、遗留风险。
```

## 默认分配策略（起点，非教条）

- **探索 10% / 主体 60% / 校验 20% / 缓冲 10%**
- 第一次就做对，比做完再返工便宜 → 侦察不要省。
- **校验环节的预算不可挪用**。省掉校验省下的 token，通常会在返工里加倍花回来，且带来静默错误。
- 若预算极小（不足以完成 G）：**先报告"预算不足"并给出最小可行子集**，不要悄悄产出半成品。

## 与已有能力对接（复用，不自研）

- **原生预算开关**：Anthropic `thinking:{type:"enabled",budget_tokens:N}`；Gemini `thinking_config.thinking_budget`；OpenAI `reasoning_effort`。
- **硬护栏**：LiteLLM 的 virtual key + `max_budget` / `budget_duration`，超支直接拒绝；把每轮 agent 的上限设为 dollar budget + 迭代次数。
- **计量**：Langfuse（或同类 trace 工具）逐 span 记 token/cost，用于 profile 与 A/B。
- **降本轮子**：prompt caching（原生）、语义缓存、prompt 压缩（LLMLingua 类）、成本路由（RouteLLM 类）。
- **动态思考控制**：借鉴 s1 的 "budget forcing" —— 到点强制收束思考、不足则引导继续自检；把它包在思考预算之上做调度。

## 反模式（出现即为错）

- 仅在回复里**声称**省了 token，但没有真实计量。
- 用"多轮对话自然变长"冒充"深思考" —— 那是失控，不是分配。
- 为了省预算跳过验证、跳过交叉确认。
- 把"塞更多上下文"当成"更高效率"。
- 单次运行就下结论：分配策略方差大，需多次运行看分布。
